# Evidence

Execution records, experiment evidence, provenance and reproducibility records.

~~~

## 1. Purpose

The `evidence/` layer contains General Factory implementation assets and records used to capture evidence generated throughout Factory activities.

Evidence may be produced by:

- Experiments
- Workflows
- Runtime execution
- Asset execution
- Simulation
- Emulation
- Validation
- Testing
- Deployment
- Resource execution
- External integrations
- Product development

```text
Definition
    ↓
Configuration
    ↓
Execution
    ↓
Observation
    ↓
Result
    ↓
Evidence
```

The purpose is to make important Factory activities traceable, reviewable and reproducible where practical.

~~~

## 2. Architectural Position

Evidence is a cross-cutting Factory capability.

```text
General Framework
      ↓
Evidence Definitions / Contracts
      ↓
General Factory
      ↓
Evidence
      ↑
      │
 ┌────┼───────────────────────────┐
 │    │       │       │           │
Assets Experiments Workflows Deployments Resources
```

Evidence is therefore not limited to experimentation.

It may be generated by any Factory activity where traceability, validation, provenance or reproducibility is required.

~~~

## 3. Evidence Versus Result

A result is an output of an execution.

Evidence provides the information needed to establish what happened and under what conditions.

```text
Execution
   ├── Result
   ├── Logs
   ├── Metrics
   ├── Configuration
   ├── Runtime State
   ├── Resource Information
   └── Provenance
             ↓
          Evidence
```

A result may therefore be one component of an evidence record.

~~~

## 4. Evidence Versus Provenance

Provenance describes the origin and history of an asset, execution or result.

Evidence is the broader record supporting an activity or conclusion.

```text
Evidence
 ├── Execution Record
 ├── Result
 ├── Configuration
 ├── Provenance
 ├── Validation
 └── Supporting Artifacts
```

Provenance should therefore be captured as part of evidence where relevant.

~~~

## 10. Configuration Evidence

Configuration that materially affects execution should be traceable.

Configuration evidence may include:

- Configuration version
- Parameters
- Environment
- Runtime settings

- Adapter configuration

## 11. Reproducibility

Evidence should support reproducibility where practical.

A reproducibility record may identify:

```text
What
 ↓
Problem / Experiment / Workflow

With what
 ↓
Assets / Implementations / Runtime

Configured how
 ↓
Configuration / Parameters

Executed where
 ↓
Environment / Resources / Backend

When
 ↓
Execution Time

What happened
 ↓
Results / Observations

What supports it
 ↓
Evidence / Provenance
```

Exact reproduction may not always be possible, particularly when external systems or nondeterministic resources are involved.

~~~

## 12. Reproducibility Levels

Different activities may require different levels of reproducibility.

Possible levels include:

```text
Level 1
Execution identity

Level 2
Configuration and version traceability

Level 3
Environment and resource traceability

Level 4
Re-executable workflow

Level 5
Reproducible result under equivalent conditions
```

These are implementation guidance rather than mandatory classifications for every activity.

~~~

## 53. Guiding Principles

1. Evidence is a Factory-wide cross-cutting capability.
2. Evidence is not limited to experimentation.
3. Execution records should identify what actually happened.
4. Results and evidence are related but distinct.
5. Provenance should identify the origin and history of relevant assets and executions.
6. Evidence should preserve configuration and implementation context where required.
7. Reproducibility should be supported where practical.
8. Actual implementation versions should be traceable.
9. Actual resource and runtime context should be traceable where relevant.
10. Simulation and emulation evidence should remain distinguishable.
11. Validation evidence should remain associated with its criteria and observed results.
12. Sensitive information should not be unnecessarily copied into evidence.
13. Evidence access must respect security and authorization policies.
14. Important evidence should have appropriate integrity and retention controls.
15. Evidence should connect requirements, assets, implementations, executions and results where appropriate.
16. Pilot evidence may support controlled post-pilot promotion.
17. Evidence supports productization decisions but does not by itself establish product readiness.
18. Machine-readable evidence should be used where practical.
19. Evidence should preserve enough context to understand and reproduce important Factory activities.
20. Evidence should remain traceable throughout the asset and implementation lifecycle.

~~~

## 54. Guiding Statement

**Evidence is the General Factory record of what was configured, executed, observed, validated and produced, together with the provenance required to understand and reproduce important activities.**

**Capture the execution context, preserve provenance, protect evidence integrity, and maintain traceability from requirement through implementation, execution and result.**
