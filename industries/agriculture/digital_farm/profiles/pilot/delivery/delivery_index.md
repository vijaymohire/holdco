# Pilot Delivery Index

## Purpose

This index provides the lightweight entry point for identifying client
deliverables from the QAI Digital Farm pilot.

It supports:

- standard full-pilot delivery
- arbitrary phase delivery
- stage-based delivery
- custom delivery

The index does not duplicate the Phase 12 Delivery Registry.

---

## 1. Standard Full-Pilot Completion

Recommended pathway:

Phase 0
→ Phase 1
→ Phase 2
→ Phase 3
→ Phase 4
→ Phase 5
→ Phase 6
→ Phase 7
→ Phase 8
→ Phase 9
→ Phase 10
→ Phase 11
→ Phase 12

Canonical delivery source:

`phase_12/delivery_registry/`

Canonical package selection:

`phase_12/delivery_selection/`

---

## 2. Arbitrary Phase Delivery

Clients may request deliverables after an agreed phase without completing
the entire 12-phase lifecycle.

Examples:

### Phase 3

Workflow / architecture / notebook package

### Phase 6

Evaluation / Advantage / value package

### Phase 7

Validation / model / evidence package

### Phase 8

Digital Twin / production-oriented transition package

### Phase 9

QAI Lab project integration package

### Phase 10

Fabric / slice integration / mapping / evidence package

### Phase 11

Benchmark / Advantage Gate / differentiation package

### Phase 12

Complete pilot / delivery / Post-Pilot package

The actual package is assembled and recorded through the Phase 12 Delivery
Registry.

---

## 3. Stage-Based Delivery

Clients may also receive deliverables according to the five client
realization stages.

### Stage 1 — See It

Possible package:

- architecture
- demonstration notebook
- synthetic data
- visualizations
- selected results
- introductory evidence

### Stage 2 — Run It

Possible package:

- CPS workflows
- simulation / emulation
- scenarios
- closed-loop results
- experiment evidence

### Stage 3 — Validate It

Possible package:

- representative / historical data
- model validation
- benchmark results
- Advantage Gate
- validation evidence

### Stage 4 — Deploy It

Possible package:

- deployment configuration
- interface definitions
- selected physical integration artifacts
- operating guidance
- safety / security boundaries

### Stage 5 — Scale It

Possible package:

- scale architecture
- distributed execution
- operations
- federation
- multi-site requirements
- Post-Pilot roadmap

Actual package contents depend on the engagement boundary.

---

## 4. Phase + Stage Combination

Delivery may be based on both:

Phase

and

Client Stage.

For example:

Stage 3 + Phase 7

→ Model Validation Package

Stage 3 + Phase 11

→ Benchmark / Advantage Gate Package

Stage 4 + Phase 12

→ Deployment / Handover Package

The Phase 12 registry remains the canonical package record.

Possible package types:

## 7. Delivery Flow

Pilot Delivery Index

→ Phase / Stage / Custom Selection

→ Package Manifest

→ Optional Post-Pilot Path

---

## 8. Asset Source Principle

The Delivery Index does not copy source assets.

It identifies where the required assets originate.

Example:

Phase 7

→ validation evidence

→ model record

→ experiment result

→ package reference

---

## 9. Canonical Delivery Location

The canonical delivery management structure is:

`phase_12/`

with the principal areas:

- `delivery_registry/`
- `delivery_packages/`
- `delivery_selection/`
- `handover/`
- `evidence/`
- `provenance/`

The pilot-level `delivery/` folder remains the entry/index layer.

---

## 10. Delivery Status

Possible statuses:

- Draft
- Selected
- Prepared
- Delivered
- Accepted
- Archived

These statuses are maintained through the appropriate Phase 12 delivery
records.

---

## 11. Delivery State Boundary

Prepared

does not necessarily mean:

Transferred

and:

Transferred

does not necessarily mean:

Operationally Accepted

These states remain distinct.

---

## 12. Client Destination

The selected package may be designated for:

- client repository
- client SharePoint
- client Git repository
- client-controlled storage
- approved shared workspace
- other controlled destination

The destination is recorded in the package manifest or handover record.

---

## 13. Optional Business Pathways

A delivery package may optionally reference:

- Product Foundry
- IP / Patent
- TTO
- SaaS / Managed Service
- Turnkey Deployment
- Further Research
- Post-Pilot Engineering

These are optional pathways.

Selecting a delivery package does not automatically initiate any of them.

---

## 14. Post-Pilot

Post-Pilot items are recorded through Phase 12.

Examples:

- scalability
- physical deployment
- multi-tenancy
- multi-cloud
- advanced optimization
- regional Digital Twin
- rural-urban CPS
- SaaS
- managed services
- turnkey implementation
- further research

The index only points to the relevant delivery / handover information.

---

## 15. Client Choice Principle

Clients may choose:

- what to see
- what to run
- what to validate
- what to receive
- what to deploy
- what to postpone
- what to continue

The delivery architecture therefore supports flexible engagement rather
than requiring one mandatory sequence.

---

## 16. No Duplicate Delivery System

This folder is only an entry/index layer.

It does not create a second:

- asset registry
- package builder
- package catalogue
- handover system
- Post-Pilot system

Those capabilities remain under Phase 12.

---

## 17. Final Principle

`pilot/delivery/` tells the client:

**Where do I begin to obtain the deliverables from my completed activity?**

`pilot/phase_12/` provides:

**The canonical registry, package selection, manifest, handover and
Post-Pilot records.**
