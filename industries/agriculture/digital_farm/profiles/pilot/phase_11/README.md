# Phase 11 — Vendor Benchmark & Differentiation

## 1. Phase Identity

Phase: 11

Name: Vendor Benchmark & Differentiation

Pilot: QAI Digital Farm

Parent Path:
industries/agriculture/digital_farm/profiles/pilot/phase_11

Primary Objective:

Benchmark relevant vendor and technology capabilities against a common problem
representation and use the Advantage Gate to determine the most appropriate
client solution approach.

---

## 2. Purpose

Phase 11 evaluates available technology and execution approaches using a
common problem representation and a controlled evidence model.

The purpose is not to rank vendors.

The purpose is to determine:

Which approach is most appropriate for the client's problem under the
client's technical, operational, resource, economic and deployment
constraints?

---

## 3. Governing Principle

Compare candidate approaches for the client problem.

Do not assume that QAI, quantum-inspired methods, hybrid methods, AI or
classical methods are automatically preferred.

The preferred approach is the one supported by evidence for the specific
client problem and constraints.

Vendor benchmarking is a capability comparison exercise.

It does not create:

- procurement systems

- vendor-dependent architecture
- procurement rankings

## 10. Common Problem Representation

All candidate approaches should use a common problem representation wherever
practical.

The representation should describe:

- decision variables
- objectives
- constraints
- state variables
- dependencies
- scenarios
- resource limits
- demand
- target values
- operating conditions
- economic assumptions
- risk assumptions

The benchmark should compare methods against the same defined problem.

---

## 11. Problem Definition Principle

The problem should be defined before selecting the preferred execution
technology.

The preferred sequence is:

Problem

→ Model

→ Constraints

→ Common Representation

→ Candidate Solvers

→ Benchmark

→ Advantage Gate

The benchmark should not be designed around a predetermined answer.

## 12. Problem Complexity

Phase 11 evaluates the structure and growth of the client problem.

Possible measurements:

- number of variables
- number of constraints
- number of states
- number of scenarios
- combination count
- dependency count
- search-space size
- branching structure
- state-space size
- executable problem size

The benchmark records how these dimensions change as problem size grows.

---

## 13. Complexity Growth

The benchmark should examine growth behaviour such as:

Problem Size

10 → 20 → 40 → 80 → ...

and observe:

- runtime
- memory
- executable scope
- solution quality
- search-space growth
- resource requirements

The purpose is to understand practical scaling behaviour.

---

## 14. Scope Reduction

FAEP does not necessarily execute the complete raw client problem directly.

The problem may first be:

- filtered
- constrained
- decomposed
- aggregated
- reduced
- grouped
- scoped
- transformed

The benchmark should therefore measure:

Raw Problem Scope

→ Modelled Scope

→ Executable Scope

where measurable.

---

## 15. Scope Reduction Principle

Scope reduction must not be described as eliminating mathematical
complexity unless that has been demonstrated.

Instead, Phase 11 may document:

- relevant-variable reduction
- scenario reduction
- constraint filtering
- decomposition
- aggregation
- search-space reduction
- executable problem reduction

The resulting execution problem should remain traceable to the original
client problem.

---

## 16. Executable Problem Size

The benchmark should distinguish between:

Original Problem Size

and

Executable Problem Size

This distinction is important because modelling and decomposition may make
the practical execution problem substantially different from the raw
problem statement.

---

=

Original Executable Scope

relative to

Post-Modelling Executable Scope

## 25. Classical Runtime Metric

- problem size
- executable scope
- runtime
- memory
- solution quality
- execution context

## 26. Hybrid Runtime Metric

Where relevant:

- preprocessing
- QAI / quantum-inspired execution
- classical execution
- post-processing
- total runtime

The total end-to-end runtime should be retained.

---

## 27. Memory Metric

Memory is a primary resource metric.

Record:

- classical memory
- hybrid memory
- QAI / QI memory
- peak memory where measurable

The same measurement conditions should be used for meaningful comparisons.

## 28. Scalability Metric

- runtime growth
- memory growth
- executable scope
- solution quality
- resource requirements

asymptotic claims without evidence.

## 54. Possible Advantage Gate Outcomes

Possible outcomes include:

- Classical Preferred
- AI Preferred
- Hybrid Preferred
- QAI / Quantum-Inspired Preferred
- Quantum Candidate Preferred
- No Material Difference
- Further Experimentation Required

These are decision outcomes for the client problem, not universal technology
rankings.

---

## 55. Classical Preferred

This result means the classical approach currently provides the required
client outcome under the evaluated constraints.

It does not mean that QAI is invalid for other problems.

---

## 56. AI Preferred

This result means AI currently provides the most appropriate validated
approach for the evaluated client problem.

---

## 57. Hybrid Preferred

This result means a combined execution path provides the most appropriate
validated result.

---

## 58. QAI / Quantum-Inspired Preferred

This result may occur when the evidence supports a QAI or
quantum-inspired/hybrid approach for the specific problem.

The conclusion remains problem-specific.

---

## 59. Quantum Candidate Preferred

This result may be recorded only when a suitable quantum execution path has
been demonstrated sufficiently for the defined evaluation boundary.

It does not imply general quantum superiority.

---

## 60. No Material Difference

Where differences are within the defined tolerance or do not materially
change the client decision:

No Material Difference

may be recorded.

---

## 61. Further Experimentation Required

If the evidence is insufficient, the correct result is:

Further Experimentation Required

rather than forcing a preferred technology.

---

## 81. Complexity Claims Discipline

practical executable problem, state that result specifically.

Do not automatically translate that result into:

- elimination of NP-hardness
- elimination of exponential growth
- polynomial-time transformation
- universal complexity reduction

Any such claim requires separate mathematical evidence.

## 109. Phase 11 Acceptance Criteria

Phase 11 is acceptable when:

1. The common problem representation is defined.
2. Candidate approaches are defined.
3. Vendor capabilities are documented as capabilities rather than rankings.
4. Complexity is measured or explicitly bounded.
5. Scope reduction is measured where applicable.
6. Classical runtime is measured.
7. Hybrid runtime is measured where applicable.
8. Memory is measured.
9. Scalability behaviour is evaluated.
10. Solution quality is considered.
11. QAI supporting metrics are correctly bounded.
12. The Advantage Gate is implemented.
13. The outcome is client-specific.
14. Differentiation statements have evidence status.
15. Claims remain within the benchmark evidence boundary.

## 110. Phase 11 Review Gate

Formal review questions:

- Is the benchmark based on a common problem representation?
- Are candidate approaches compared fairly?
- Is the vendor benchmark capability-based?
- Has unnecessary vendor complexity been avoided?
- Are complexity and growth behaviours recorded?
- Is executable scope reduction measurable?
- Are runtime and memory measured consistently?
- Is solution quality included?
- Is the Advantage Gate client-specific?
- Are QAI and VirtualQubit claims properly bounded?
- Are differentiation claims evidence-based?
- Does the benchmark preserve provider neutrality?
- Can the benchmark support Greenfield and Brownfield engagements?

---

## 111. Formal Review Outcomes

Possible outcomes:

PASS

Phase 11 benchmark and Advantage Gate are acceptable and Phase 12 may begin.

REVISE

Benchmark scope, metrics, evidence or decision logic requires correction.

HOLD

Required benchmark information or implementation evidence is not yet
sufficient.

No Phase 12 implementation should silently bypass the review gate.
